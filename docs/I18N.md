# Internationalisation

The site ships in three locales: English at `/`, Arabic at `/ar`, French at `/fr`.
Routing is `next-intl` in `as-needed` mode, so English is unprefixed:

- English event: `/era/meccan/mec-007`
- Arabic event: `/ar/era/meccan/mec-007`
- French event: `/fr/era/meccan/mec-007`

`src/i18n/routing.ts` is the single source of truth. The language switcher and the sitemap
both read it, so adding a locale there surfaces it everywhere. The middleware at
`src/proxy.ts` is a thin wrapper around `createMiddleware(routing)`. Import `Link`,
`useRouter`, and `usePathname` from `@/i18n/navigation`, never from `next/navigation`; the
wrappers preserve the locale across navigation.

## Where text lives

**`messages/{en,ar,fr}.json`** hold UI chrome only: page titles, buttons, navigation,
breadcrumbs, category labels, and the about page paragraphs. Namespaces are `site`, `nav`,
`home`, `timeline`, `era`, `event`, `breadcrumb`, `about`, `footer`, `notFound`,
`categories`. All three files carry the same key set.

**`data/events/*.json`** hold the events. Narrative fields use an English base name with a
language suffix:

| Field | Arabic | French |
|---|---|---|
| `title` | `titleArabic` | `titleFrench` |
| `summary` | `summaryArabic` | `summaryFrench` |
| `significance` | `significanceArabic` | `significanceFrench` |
| `location` | `locationArabic` | `locationFrench` |
| `era.description` | `descriptionArabic` | `descriptionFrench` |

All 49 events and all 3 era descriptions carry Arabic and French summaries and
significance. The English remains the source of record; the Arabic and French are faithful
translations of it, preserving every fact, name, date, and citation.

Read these through `localizedField(source, base, locale)` from `src/lib/localized.ts`. It
returns both the text and the language it actually resolved to, because the caller needs
that second value to set `lang` and `dir` correctly when it falls back. Never index the
field directly: `event.summaryArabic` renders Arabic on the French site.

## Proper nouns are not stored per locale

Companions, opponents, groups, hadith narrators, cited works, authors, Hijri months, and
surah names are resolved at render time:

- `src/config/names.ts` for works, authors, months, and surahs
- `src/config/figures.ts` for people and groups

This keeps the event data free of per-locale name duplication. A name with no registry
entry falls back to English rather than failing, so a new event does not break the build;
that one name simply renders in English until the registry catches up.

## Dates and numerals

`src/lib/dates.ts` is the only date formatter. Arabic gets Arabic month names, Eastern
Arabic numerals, and `ق.هـ` / `هـ` / `م`. French gets `av. H.` / `H.` / `ap. J.-C.`.

Do not format dates inline. The stored values are not uniform: some carry qualifiers such
as `44 BH onwards` or `Ramadan (17th or 21st)`, and a regex anchored to the end of the
string silently leaves the era marker in place. Qualified month strings resolve through the
`MONTH_NAMES` registry rather than word-by-word substitution, because substitution leaves
the English connective behind.

## Direction and fonts

The locale layout sets `dir` and `lang` on `<html>`: `rtl`/`ar` for Arabic, `ltr` for
English and French. Arabic body text uses IBM Plex Sans Arabic; English and French use
Source Serif 4. Amiri remains the family for Quranic verses and classical Arabic through
`font-arabic`, on every locale.

When mixing scripts on one line, wrap the inner-direction content in a span carrying `dir`
and `lang`. That markup is what makes a screen reader switch voice, and the locale scanner
uses the same attribute as the signal that the foreign script is deliberate. Logical CSS
properties (`start`, `end`, `me`, `ms`, `pe`, `ps`) handle the rest; the timeline spine,
breadcrumb chevrons, and prev/next arrows flip on RTL through `rtl:scale-x-[-1]`.

## The religious content rule

The application never produces, modifies, or invents Quran, hadith, or seerah text.

Quran text in all three languages comes from a published edition through
`npm run fetch:scripture`: Uthmani in Arabic, Saheeh International in English, Hamidullah
in French. The script fetches the full cited ayah range in each edition, so the Arabic and
both translations always describe the same passage. Nothing in that path is translated
here, which is what `translationProvenance: "fetched"` records.

Hadith is different. The English excerpt in an event is the project's own abridgement, not
a published translation, so the French was produced the same way and both carry
`translationProvenance: "project"`. `textArabic` is the matn read from the collection, so
the Arabic locale shows the source rather than a rendering of it. Grep for `"project"` to
list the entries a reviewer should read.

Titles, locations, summaries, and significance paragraphs are the project's own prose and
are translated in full.

## Verifying

```bash
npm run verify:citations
npm run build && npx next start -p 3000
LOCALES=ar,fr node scripts/verify-locales.mjs http://localhost:3000 / /timeline /about
```

The scanner renders every route in every locale and reports text whose script disagrees
with the page, skipping anything carrying an explicit `lang`.
`scripts/i18n-allowlist.json` holds the exceptions, one reviewable line each.

Run it against `next start`, not `next dev`. The production build is what ships.

The scanner compares scripts, so it cannot see English left on the French locale: both are
Latin. That class of gap has to be found by reading, which is how the 49 English event
titles and 49 English locations on `/fr` were found after the scanner reported clean.

## Adding a locale

1. Add the code to `routing.ts`, plus entries in `localeDirection` and `localeNames`.
2. Copy `messages/en.json` and translate every value.
3. Add the narrative suffix to `SUFFIX` in `src/lib/localized.ts`.
4. Add the locale to every entry in `src/config/names.ts` and `src/config/figures.ts`.
5. Add `<field><Suffix>` values across `data/events/*.json`.
6. Add the OG locale to `OG_LOCALES` in `src/lib/metadata.ts`.
7. Run the scanner against a production build.
