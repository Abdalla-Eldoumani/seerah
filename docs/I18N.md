# Internationalisation

The site ships in three locales: English at `/`, Arabic at `/ar`, French at `/fr`. Routing is `next-intl` in `as-needed` mode, so English is unprefixed:

- English event: `/era/meccan/mec-007`
- Arabic event: `/ar/era/meccan/mec-007`
- French event: `/fr/era/meccan/mec-007`

`src/i18n/routing.ts` is the single source of truth for the locale list, the text direction of each locale, and the native names the language switcher shows. The URL decides the locale: detection and the locale cookie are off, so nothing is written to a visitor and the pages stay cacheable. Import `Link`, `useRouter`, and `usePathname` from `@/i18n/navigation`, never from `next/navigation`; the wrappers keep the locale across navigation.

## Where text lives

**`messages/{en,ar,fr}.json`** hold interface text only: page titles, buttons, navigation, breadcrumbs, category labels, era names, and the about page. Namespaces are `site`, `nav`, `home`, `timeline`, `era`, `event`, `breadcrumb`, `about`, `footer`, `notFound`, and `categories`. All three files carry the same keys.

**`data/events/*.json`** hold the events and the era blocks. Narrative fields use the English name for English and a suffix for the other two:

| Field | Arabic | French |
|---|---|---|
| `title` | `titleArabic` | `titleFrench` |
| `summary` | `summaryArabic` | `summaryFrench` |
| `significance` | `significanceArabic` | `significanceFrench` |
| `location` | `locationArabic` | `locationFrench` |
| era `description` | `descriptionArabic` | `descriptionFrench` |

English is the source of record. The Arabic and French fields are the project's own renderings of it, written in those languages, and this repository holds no record of a review by a native-speaking reader. Treat them as unreviewed until one is noted here. The interface strings added with the route line (`route.from`, `route.to`) and the event counter (`event.position`) are in the same state.

Read these fields through `localizedField(source, base, locale)` in `src/lib/localized.ts`. It returns the text and the language that actually resolved, because the caller needs that to set `lang` and `dir` when it falls back to English. Indexing a field directly is a bug: `event.summaryArabic` renders Arabic on the French site.

## Proper nouns are not stored per locale

People, groups, hadith narrators, works, authors, Hijri months, and surah names are resolved at render time from registries:

- `src/config/names.ts` for works, authors, months, year phrases, and surahs
- `src/config/figures.ts` for people, groups, and narrators

At render time a name with no entry falls back to the English spelling, so an Arabic reader would see Latin script inside Arabic prose. `scripts/verify-names.mjs` closes that gap before it ships: `npm run build` fails when any name in the event data lacks an Arabic or French form.

## Dates and numerals

`src/lib/dates.ts` is the only date formatter.

- **Arabic** shows Arabic month names, Eastern Arabic numerals for Hijri years and months, and the suffixes `ق.هـ` (before the Hijrah), `هـ`, and `م` (Gregorian). Gregorian years keep Western digits. An approximate date opens with `نحو`. The comma is `،`.
- **French** shows `av. H.`, `H.`, and `ap. J.-C.`, and `vers` for an approximate date.

Do not format dates inline. The stored values are not uniform: some carry qualifiers such as `44 BH onwards` or `Ramadan (17th or 21st)`, so the formatter strips era markers by token rather than by pattern and resolves qualified months as whole strings, because word-by-word substitution leaves the English connective behind.

## Direction and fonts

The locale layout sets `dir` and `lang` on `<html>`: `rtl` and `ar` for Arabic, `ltr` for English and French. On Arabic pages the display and body stacks switch to IBM Plex Sans Arabic; English and French use Alegreya for headings and IBM Plex Sans for text. Amiri is the family for Qur'anic verses and classical Arabic on every locale, through `font-arabic`. A small `Salawat` face supplies U+FDFA, which none of the others draw well.

When scripts mix on one line, wrap the inner-direction content in an element carrying `dir` and `lang`. That markup makes a screen reader switch voice, and the locale scanner reads the same attribute as the signal that the foreign script is deliberate. Two helpers do this: the `rich` tags in `src/lib/rich.tsx` mark a Latin name inside a translated message (`<en>sunnah.com</en>` in `messages/ar.json`, rendered with `t.rich(key, rich)`), and `markLatinRuns` in `src/lib/latin-runs.tsx` marks Latin runs in Arabic event prose at render time. Logical CSS properties (`start`, `end`, `ms`, `me`, `ps`, `pe`) handle the rest; chevrons and arrows flip on RTL with `rtl:scale-x-[-1]`.

## The religious content rule

The application never produces, modifies, or invents Qur'an, hadith, or seerah text.

Qur'an passages come from published editions through `npm run fetch:scripture`: Uthmani for Arabic, Saheeh International for English, Hamidullah for French. The script fetches the whole cited ayah range in each edition, so the three always describe the same passage. Nothing in that path is translated by the project, which is what `translationProvenance: "fetched"` records. The Arabic locale shows the verse alone.

Hadith differ. For the 52 references read at sunnah.com, `textArabic` and `textEnglish` are pasted from the page for that collection and number (`translationProvenance: "sunnah"`). sunnah.com publishes no French, so French pages show the English with a note saying so. For the two narrations no sunnah.com collection carries, the Arabic was read at dorar.net and the English and French are the project's own renderings, marked `translationProvenance: "project"` and labelled beside the text. Search the data for `"project"` to list every entry a reviewer should read against its Arabic.

Titles, locations, summaries, and significance paragraphs are the project's own prose.

## Verifying

```bash
npm run verify:citations
npm run verify:names
npm run build && npx next start -p 3000
LOCALES=ar,fr node scripts/verify-locales.mjs http://localhost:3000 / /timeline /about /era/meccan /era/meccan/mec-007
```

The scanner fetches each route you pass in each locale and reports text whose script disagrees with the page: Latin text on `/ar`, Arabic text on `/fr`. It skips anything inside an element with an explicit `lang`. `scripts/i18n-allowlist.json` holds the exceptions, one reviewable line each.

Run it against `next start`, not `next dev`, because the production build is what ships.

The scanner compares scripts, so it cannot see English left on the French locale: both are Latin. That gap has to be found by reading.

## Adding a locale

1. Add the code to `routing.ts`, plus entries in `localeDirection` and `localeNames`.
2. Copy `messages/en.json` and translate every value.
3. Add the narrative suffix to `SUFFIX` in `src/lib/localized.ts`.
4. Add the locale to every entry in `src/config/names.ts` and `src/config/figures.ts`, and to the lookups that read them.
5. Add the suffixed fields across `data/events/*.json`.
6. Add the OpenGraph locale and BCP 47 tag to `OG_LOCALES` and `BCP47` in `src/lib/seo.ts`.
7. Pick a font for the script and add it in `src/lib/fonts.ts`; add a face to the share-card route if it needs one.
8. Run the scanner against a production build.
